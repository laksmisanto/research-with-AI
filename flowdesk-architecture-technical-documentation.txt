1. Product Overview
Flowdesk is a personal productivity platform combining Trello-style Kanban boards with Notion-style rich text notes. It is designed for three core user personas — Developers/Designers, Students, and Researchers — each getting a tailored experience within a shared architecture.

1.1 Core Philosophy
One app, three personas — same codebase, same data model, different UI modes
Workspace-first — everything lives inside a Workspace, enabling future multi-user support
Card = Task + Document — every Kanban card contains a full TipTap rich-text page
Local-first storage — files stored locally in MVP, Cloudinary-ready for production
Expandable schema — multi-user, sharing, and collaboration can be added without restructuring

2. System Architecture

2.2 Communication Flow
The data flow for a typical user action (e.g. creating a card) follows this path:

User interacts with the Next.js frontend (React component)
Zustand store dispatches action → TanStack Query mutation fires
Axios sends HTTP request to Express.js backend (port 5000)
Express middleware: JWT verify → route handler → controller
Controller calls Mongoose model → MongoDB reads/writes data
Response flows back: MongoDB → Mongoose → Controller → Express → Axios → TanStack Query → Zustand → UI re-render

2.3 Authentication Strategy
Access Token: JWT, short-lived (15 minutes), stored in memory (Zustand)
Refresh Token: Long-lived (7 days), stored in httpOnly cookie
On access token expiry: silent refresh via /auth/refresh endpoint
Logout: refresh token deleted from DB and cookie cleared
Future multi-user: same auth system, just add workspace membership checks

4. Database Schema (MongoDB + Mongoose)
All collections use MongoDB ObjectId references. The schema is designed to be workspace-scoped, making multi-user expansion straightforward — just add membership checks.

4.1 users Collection
Stores authentication and profile data for every user. The persona array allows users to switch between Developer, Student, and Researcher modes within the same account.

{
  _id:         ObjectId,
  name:        String (required),
  email:       String (required, unique, lowercase),
  password:    String (bcrypt hashed),
  avatar:      String (file path → cloudinary url later),
  persona:     [String]  // ["developer", "student", "researcher"]
                         // multi-select, user can have all three
  refreshToken: String   // stored for refresh token rotation
                         // null on logout
  createdAt:   Date,
  updatedAt:   Date
}
Key design decisions:
Password is never returned in API responses (select: false on schema)
persona is an array so one account can track dev work AND study plans
refreshToken stored in DB enables token rotation and logout-all-devices in future

4.2 workspaces Collection
A Workspace is the top-level container. Every project, note, and folder belongs to a workspace. This is the key to future multi-user support — just extend the members array.

{
  _id:       ObjectId,
  owner:     ObjectId → users (required),
  name:      String (e.g. "My Dev Work", "PhD Research"),
  type:      String  // "work" | "study" | "research" | "personal"
  icon:      String  // emoji or icon name (e.g. "💻", "📚")
  color:     String  // hex color for sidebar accent
  members: [
    {
      user: ObjectId → users,
      role: String  // "owner" | "member" | "viewer"
    }
  ],
  createdAt: Date,
  updatedAt: Date
}
Key design decisions:
In MVP, members array has only the owner — no multi-user logic needed yet
type field drives which UI modules are shown (study plan tab for "study" workspaces)
Adding a new team member later = push to members array, no schema change

4.3 projects Collection
A Project lives inside a Workspace. It can be a Kanban board (for tasks), a Study Plan (for students), or a Research Project (for researchers). The type field controls which views are available.

{
  _id:         ObjectId,
  workspace:   ObjectId → workspaces (required),
  owner:       ObjectId → users (required),
  name:        String (required),
  description: String,
  type:        String  // "kanban" | "study" | "research"
  color:       String  // accent color shown in UI
  tags:        [String],
  progress:    Number  // 0-100, auto-calculated from cards
  dueDate:     Date,
  isArchived:  Boolean (default: false),
  createdAt:   Date,
  updatedAt:   Date
}
Key design decisions:
"kanban" type → shows Columns + Cards view
"study" type → shows Study Plan timeline + progress % per topic
"research" type → shows research phases + reference manager
progress is stored (not computed on every read) and updated when cards change

4.4 columns Collection
Columns represent the stages in a Kanban board (e.g. Todo → In Progress → Done). Each column belongs to one project. The position field is a floating-point number to support drag-and-drop reordering without updating all sibling positions.

{
  _id:       ObjectId,
  project:   ObjectId → projects (required),
  title:     String (required, e.g. "Todo", "In Progress", "Done"),
  position:  Number   // drag-drop order — use float (1.0, 2.0, 3.0)
                      // insert between: avg of neighbors (1.5)
                      // reindex when gaps get too small
  color:     String   // optional column accent color
  createdAt: Date,
  updatedAt: Date
}

4.5 cards Collection
Cards are the core unit of Flowdesk. Each card is both a task (with status, priority, due date) and a document (with a full TipTap rich-text page). This is the Trello + Notion hybrid in one record.

{
  _id:       ObjectId,
  column:    ObjectId → columns (required),
  project:   ObjectId → projects (required),
  title:     String (required),


  // Notion-like document (TipTap JSON)
  content:   Object   // TipTap editor JSON output
                      // stored as Mixed type in Mongoose


  priority:  String   // "low" | "medium" | "high" | "urgent"
  tags:      [String],


  // File attachments (local MVP → Cloudinary later)
  attachments: [
    {
      name:  String,
      path:  String  // local: "uploads/filename.pdf"
                     // production: cloudinary URL
      type:  String  // "pdf" | "image"
      size:  Number  // bytes
    }
  ],


  // External links (developer-specific)
  links: [
    {
      label: String  // "Figma Design", "PR #42"
      url:   String,
      type:  String  // "github" | "figma" | "other"
    }
  ],


  dueDate:     Date,
  position:    Number   // float, same reorder strategy as columns
  isCompleted: Boolean (default: false),
  createdAt:   Date,
  updatedAt:   Date
}
Key design decisions:
content stored as Mongoose Mixed type — TipTap outputs JSON, we store it as-is
position uses float strategy — no need to update all cards on every drag
attachments array supports both local paths and Cloudinary URLs — migration is just updating the path string
links array is optional — only rendered in Developer persona UI

4.6 notes Collection
Notes are standalone documents not tied to any card or project. This is the pure Notion side of Flowdesk — personal research notes, study notes, quick captures. They live in Folders and support the same TipTap editor as cards.

{
  _id:       ObjectId,
  owner:     ObjectId → users (required),
  workspace: ObjectId → workspaces (required),
  folder:    ObjectId → folders (nullable)
             // null = root level (no folder)


  title:     String (required),
  content:   Object   // TipTap JSON
  type:      String   // "personal" | "research" | "study"
  tags:      [String],


  // File attachments (same structure as cards)
  attachments: [
    { name, path, type, size }
  ],


  // Research references (researcher persona only)
  references: [
    {
      title:   String,  // paper/book title
      authors: String,  // "Smith, J., Doe, A."
      url:     String,
      year:    Number,
      journal: String   // optional
    }
  ],


  isPinned:   Boolean (default: false),
  isArchived: Boolean (default: false),
  createdAt:  Date,
  updatedAt:  Date
}
Key design decisions:
references array is only populated for research-type notes — ignored in other personas
isPinned lets users keep important notes at the top of the list
folder: null means the note is at the root level of the workspace

4.7 folders Collection
Folders organize notes. They support nesting via the parentFolder self-reference, allowing a tree structure (e.g. Research > Papers > 2024).

{
  _id:          ObjectId,
  owner:        ObjectId → users (required),
  workspace:    ObjectId → workspaces (required),
  name:         String (required),
  parentFolder: ObjectId → folders (nullable)
                // null = root folder
                // ObjectId = nested inside another folder
  createdAt:    Date,
  updatedAt:    Date
}

7. Key Technical Decisions

Why MongoDB over PostgreSQL for this project?
TipTap content is a nested JSON object — stores naturally as a MongoDB document
attachments and links as embedded arrays avoids join tables
Schema flexibility is useful in early phases when content structure may evolve
Note: for complex multi-user queries later, PostgreSQL would be stronger — but MongoDB is the right call for MVP

Why float positions for drag-and-drop?
Integer positions (1, 2, 3...) require updating all sibling records on every reorder
Float positions: insert between card 2.0 and 3.0 → assign 2.5. Only one DB write
When gaps get too small (< 0.001), reindex all cards in the column

Why TipTap for the editor?
You already use it in bdnewsfeed CMS — same knowledge, no learning curve
Outputs clean JSON (not HTML string) — easy to store, query, and export
Extensible: add code blocks, mentions, file embeds as the app grows

Why dnd-kit over react-beautiful-dnd?
react-beautiful-dnd is deprecated and unmaintained since 2023
dnd-kit is the current standard — better performance, accessibility, and TypeScript support
You have prior exposure from the NRCS architecture work

Multi-user expansion path
Every collection already has owner: ObjectId and workspace: ObjectId
Adding multi-user = add project_members checks in middleware, nothing else changes
The members array in Workspace is already in the schema — just not enforced in MVP
